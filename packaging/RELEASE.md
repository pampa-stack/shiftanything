# Pubblicazione della beta

Le release del catalogo raccolgono almeno 20 nuove verifiche rispetto alla beta pubblicata, sommando i cicli di pacchetto su Mac Apple Silicon e Linux x64, insieme alle funzioni completate. I due lotti di verifica avanzano in parallelo. Le correzioni urgenti a download, installazione o aggiornamenti del launcher si pubblicano appena superano il collaudo.

1. Scegli un commit, con la stessa versione in Cargo e Tauri. Per una release del catalogo usa `python3 packaging/release-notes.py "$commit" --previous "$ultima_release_pubblica" --changes novita.md > release-notes.md`. Se il totale è inferiore a 20, lo script restituisce il conteggio per piattaforma e termina prima della compilazione. Usa lo stesso commit per il DMG notarizzato, il DEB e il setup Windows. Per una correzione urgente al launcher ometti `--previous`.
2. Compila il setup Windows x64 dallo stesso commit, in un Windows 11 x64 con Rust MSVC, Visual Studio Build Tools e Tauri CLI. Imposta `SHIFT_LAUNCHER_UPDATE_ENDPOINT` e `SHIFT_LAUNCHER_UPDATE_PUBKEY` come per Mac e Linux, poi dal prompt di sviluppo x64 esegui `powershell -File packaging\windows\release-nsis.ps1 -SourceCommit $commit -Authenticode off -OutputDirectory <nuova cartella>`. Lo script controlla le versioni, compila con `windows-lifecycle`, verifica che setup ed eseguibile non siano firmati e scrive `windows-receipt.json` con versione, commit e SHA-256. La chiave degli aggiornamenti resta sul Mac.
3. Verifica i pacchetti su Mac Apple Silicon e Ubuntu x64. Esegui [il packaging Mac](macos/README.md) e `package-tauri-updater.sh VERSION DMG DMG_SHA256 DEB DEB_SHA256 SETUP SETUP_SHA256 OWNER/REPO OUTPUT` per firmare gli aggiornamenti delle tre piattaforme, generare `latest.json` e produrre il `.tar.gz` Linux x64 dallo stesso DEB. Lo script rifiuta un setup che non sia l'installer NSIS di ShiftAnything della versione indicata. Per generare il solo archivio usa `bash packaging/linux/portable-tar.sh VERSION DEB DEB_SHA256 OUTPUT_DIRECTORY`. Verifica l'avvio dall'archivio su una distribuzione supportata diversa da Ubuntu. Il launcher portatile si aggiorna scaricando il nuovo archivio.
4. Carica il DMG, gli aggiornamenti firmati, il `.tar.gz` Linux, il setup Windows con la sua `.sig`, il manifest e i checksum in una bozza GitHub con `--target "$commit"` e `--notes-file release-notes.md`. Controlla che i file caricati corrispondano ai checksum prima di pubblicare come release più recente.
5. Verifica il download anonimo dalla landing e l’aggiornamento dalla beta precedente sui tre sistemi. Su Windows scarica il setup con Edge, così il file riceve il Mark of the Web e SmartScreen interviene come per gli utenti. La landing legge versione, peso e download da GitHub. Il README rimanda alle note per i conteggi.

## Windows senza firma Authenticode

Il setup Windows esce senza firma Authenticode. Al primo avvio SmartScreen mostra «Windows ha protetto il PC»: l'utente clicca «Ulteriori informazioni» e poi «Esegui comunque». Windows si pubblica quando arriva a 50 app verificate; in quella release i README aggiungono la riga Windows 11 (x64) alla tabella dei download e, sotto la tabella, IT «Windows potrebbe mostrare "Windows ha protetto il PC": clicca Ulteriori informazioni e poi Esegui comunque.» ed EN «Windows may show "Windows protected your PC": click More info, then Run anyway.» Sui PC con Smart App Control attivo un setup senza firma viene bloccato senza «Esegui comunque»; lì serve la firma Authenticode. [Prova del 28 novembre 2026](../docs/verification/shiftanything-windows-ax42/unsigned-update/README.md). Gli aggiornamenti del launcher restano firmati con la chiave Tauri: il launcher installato rifiuta un setup senza firma valida, con una versione diversa da quella firmata o scaricato da un host diverso da quello del manifest.

## Accendere la firma Authenticode

La firma usa [jsign](https://github.com/ebourg/jsign) (Apache-2.0) tramite `bundle.windows.signCommand` di Tauri ed è spenta finché non c'è un certificato. Per accenderla:

1. Compra un certificato di firma del codice e conserva le credenziali in 1Password. jsign supporta file PKCS#12, token hardware e servizi cloud come Azure Trusted Signing, Google Cloud KMS e DigiCert ONE (`--storetype`).
2. Nel Windows di build installa Java e scarica il JAR di jsign, verificandone lo SHA-256 dalla release ufficiale.
3. Imposta queste variabili d'ambiente: `SHIFT_WINDOWS_SIGN_JSIGN` (percorso del JAR), `SHIFT_WINDOWS_SIGN_STORETYPE`, `SHIFT_WINDOWS_SIGN_KEYSTORE`, `SHIFT_WINDOWS_SIGN_ALIAS`, `SHIFT_WINDOWS_SIGN_STOREPASS`, `SHIFT_WINDOWS_SIGN_TSAURL` (marca temporale RFC 3161) e `SHIFT_WINDOWS_SIGN_SUBJECT` (subject esatto del certificato). La password arriva a jsign come `env:SHIFT_WINDOWS_SIGN_STOREPASS`, mai negli argomenti.
4. Esegui `release-nsis.ps1` con `-Authenticode required`. Lo script si ferma se manca una variabile, firma eseguibile, uninstaller e setup con `packaging/windows/jsign-sign.ps1` e controlla setup ed eseguibile con `verify-release-signature.ps1`. Con `-Authenticode off` lo script si ferma se trova una di quelle variabili, così una configurazione a metà non produce in silenzio un setup non firmato.
5. La firma dell'aggiornamento si fa dopo, sul Mac, sul setup già firmato Authenticode: prima Authenticode, poi SHA-256, poi la firma Tauri.
